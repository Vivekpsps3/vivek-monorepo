# Common acceptance contract

These rules apply to every new revamp leaf in addition to its own concrete rows.
They are selected delivery requirements, not a claim of completed implementation.

## Small issues

Each issue changes one user journey, small room, data contract or bounded asset set.
It has one authoritative owner, named consumers, a complete success/correction/error
path, dependencies and deletion evidence. A room issue includes actual actions and
data, not empty buttons. A contract issue serves the named next UI and has meaningful
API/model proof; no speculative framework. If real scope exceeds a focused small PR,
amend the split while retaining every requirement before implementing a partial leaf.

## Always preserve

- One domain record/calculation/write owner; existing key/AAD/record/recovery formats,
  revisions, atomicity and owner/session eligibility. Private Finance, Health,
  reflection and selected note/binding plaintext stays in the browser vault.
- Independent source states: loading, ready, absent, empty, stale, unavailable,
  expired and locked as applicable; a timeout is never a factual empty result.
- Exact source identity and occurrence dates; Town clock, Sunday/ISO/Life spans,
  birthday privacy, leap days and Travel/Finance currency/total differences.
- List/table and keyboard parity; 44px targets, contrast, first-invalid focus,
  dialog trap/Escape/return, 390×844 and1280×800 in light/night. Add320px and200%
  text zoom stress for shared layout/scene work. Check touch and reduced motion.
- Late work cannot publish after owner, route, lock or generation changes. Failed
  saves/conflicts preserve safe current-owner drafts; invalidation clears plaintext.
- Supported existing data and immutable migrations survive. A renderer deletion
  is not authorization to delete concepts, notes, layouts or financial records.

## Source and failure stories

Use F0 first visit/empty/locked, F1 ordinary daily/weekly life, F2 at least three
years of rich/truncated history, F3 partial/unavailable/stale sources, F4 two owners
with held operations and unique synthetic markers, F5 long absence, corrected/deleted
sources and cross-device conflict. The [prior fixture definitions](../living-world/acceptance.md)
remain useful with World presentation replaced by dated Town/Pixels visits.

Exercise open/create/edit/delete/Undo/search/filter/sort/page/import/refresh as
relevant, direct links, reload and Back/Forward. No hidden coverage hole is passed
to a generic final QA issue. Each implementation leaf fixes its own failing rows.
The integration leaves audit evidence and complete journeys; they do not authorize
silent feature deferral or gate reduction.

## Art and interaction

Directly select buildings/objects; no avatar controls. Actual paint and pick bounds
agree through resize/pan/zoom and occlusion. Drag never triggers a click action.
Scenes and practical lists/forms/charts all follow the selected coastal isometric
art language. Beauty, usefulness and fun require actual owner review with recorded
feedback; an agent capture or green test is not independent visual approval.

Initial assets are original or appropriately licensed, with source attribution,
palette/state variants and object metadata. Inputs and numbers stay legible. Both
the cinematic room and its compact task panel are authored. Samples are clearly
labeled and never create real records or pretend to be the owner's history.

## Rewards and corrections

The [design](design.md) fixes Stamps, prices, chapters, residents, discoveries and
minigame rules. Assert reward identities, repeat/retry behavior, concurrent spend,
refund eligibility and Town-clock day caps. Game actions cannot create real-life
records or accept private Health/Finance proof. Life-source corrections retract
derived displays without minting currency. Existing milestones, XP and badges keep
their own authoritative rules and IDs.

## Performance and verification

Retain current server/source limits and TOWN-02's600ms p50 passive-history gate.
Measure against a recorded reference profile: pending response≤100ms, confirmed
feedback within one applied-response frame, p95 pan/selection work≤16.7ms, no new
steady-pan task>50ms, zero continuous hidden/idle animation. Per scene-route delta
budget is150KiB compressed lazy JS and300KiB initial transferred art. Optional
variants/audio load lazily; no per-object/day N+1 reads or year-grid original photos.
Budget changes require measured evidence and explicit amendments, never faster
empty fixtures or removed assertions.

`plan.py launch KEY` expands each packet's profiles. All new leaves include the
docs/fast profile; actual changed sources add every root/app gate. Preserve Python
lint/types/coverage, affected Angular Karma, node/runtime tests, production build
and real Playwright journeys. Listing tests is not execution. Write exact results,
tested SHA, acceptance/deletion evidence and handoff in the existing evidence owner.

## Completion and rollout

Close a leaf only after its own full outcome. Tracking scopes stay open until all
assigned original and expanded rows have merged proof. Do not reopen historical
completed deliveries as another backlog. Planning PRs/issue publication authorize
no production configuration, purchases, notifications, merge or deployment.
Connector activation, owner art approval and release/rollback evidence remain
separate concrete outcomes. Do not commit real keys, private notes/photos or CSVs.
