# Backend contracts, data migration, and release consistency

## Ownership and transaction contract

Production is one modular application with shared SQLite, not three independent databases. The unified schema is assembled by `apps/server/schema.py` from app models and maintained by `apps/server/alembic`. Finance's historical Alembic chain and standalone init functions are not the production migration target.

- [ ] Root server owns engine/session, request transaction, shared principal/session/CSRF, settings, exception/logging middleware, offline migrations and release readiness.
- [ ] Each app owns its domain tables, serializers, business rules and provider adapters. Shared UI/platform never becomes a universal Trip/Media/Finance entity layer.
- [ ] Move user/session/account models and identity behavior out of Finance without changing existing table names, data, passwordless challenge semantics or encryption protocol.
- [ ] Provider calls occur before opening a write unit of work, or after committing a minimal saved operation. Ordinary library/detail reads do not call external services.
- [ ] One safe principal flows through domain requests; all ownership predicates remain required. Test two users and exception/cancellation cleanup.
- [ ] Shared platform modules must not import domains; factory composes them. This avoids cyclic auth/database imports while preserving explicit dependencies.

## Contract changes to freeze before parallel UI work

| Contract | Required shape / behavior | Primary owner |
| --- | --- | --- |
| Session | Authenticated identity and expiry/rotation state, CSRF assurance, safe return URL; no vault requirement | Platform |
| Finance browser summary | Locked/unavailable/ready snapshot computed by Finance facade; no decrypted server persistence | Finance |
| Error | Safe code/message, field errors, retry metadata, request ID; provider auth never suite HTTP 401 | Platform + domains |
| PTO allocation | Per-trip/date amount with explicit default/override and legacy mode; one derived total | Travel + migration |
| Flight | Source identity/fetched_at, airport zones, scheduled/estimated/actual instants, manual override provenance | Travel |
| Place lookup | Candidate identity/label/coords, match selection, cache freshness, typed failure/no-match | Travel |
| Library card | Explicit membership ID, public catalog identity, personal state/rating/effective image; no whole discography | Media |
| Music relationship | Provider/internal identities, artist credits and album/recording links, save state distinct from existence | Media |
| Artist state/art | Following relationship and per-user image override; independent rating/review | Media |
| Search | Ephemeral public results, per-source attempted/configured/status/freshness, continuation, private saved flags attached later | Media |
| TV state | Personal intent, aired progress/metadata completeness, lifecycle provenance, next/upcoming episode | Media |
| Caught-up operation | Explicit aired cutoff/scope, idempotent batch, changed marks and safe undo | Media |

Use ordinary typed schemas for these changed endpoints. Do not replace the entire backend with autogenerated CRUD or create an adapter interface hierarchy for hypothetical sources.

## DB-01 — Travel allocation migration

Recommended minimum: app-owned `TripPtoDay` rows keyed uniquely by trip/date, with amount, explicit override/default provenance, and optional migration provenance. Owning trip supplies the user relationship; add/verify appropriate ownership/index/FK constraints. Validate finite nonnegative bounded day values and date within trip. Update schema ownership checks if new directly owned tables carry user_id.

- [ ] Fresh automatic trip expands weekdays to 1 and weekends to 0, using one canonical allocation model. Storing only exceptions is acceptable if defaults are versioned and deterministic; do not implement both strategies.
- [ ] Existing automatic trips preserve their recorded weekday counts and user input; explicit aggregate zero remains zero. Per-day deductions intentionally change some intermediate/capped-accrual forecasts compared with trip-start charging. Add old/new capped and mid-balance fixtures, document the correction, and avoid promising identical projections.
- [ ] Custom legacy aggregate totals remain labeled legacy/unallocated until chosen dates can be confirmed. Store the original total/mode; preserve all forecast amounts under compatibility behavior.
- [ ] Manual PTO entries remain their own operation, sharing the canonical projection logic. Do not infer dates for an arbitrary past total.
- [ ] New allocation edits update total/forecast atomically; old editable aggregate path becomes read-only legacy handling, then is deleted once no required consumer remains.
- [ ] Date shortening, cancellation, trip deletion and overlap use specified business rules and transaction rollback on validation failure.

## DB-02 — Media migration

- [ ] Add private artist relationship/artwork override fields or table; preserve public provider default art. Avoid rewriting the shared catalog image on personal selection.
- [ ] Add normalized series lifecycle and source/freshness/completeness fields in the smallest suitable app-owned structure. Separate from UserEntry status.
- [ ] Define canonical music public identity/relationships without collisions among MusicBrainz artist/release-group/release/recording namespaces. Existing CatalogItem uniqueness is source/source_id; inspect compatibility before changing uniqueness to include kind.
- [ ] Build a deterministic mapping from legacy MusicAlbum/MusicTrack to first-class catalog/entry records. Use provider IDs where present; ambiguous manual rows get explicit provenance and conflict report.
- [ ] Create personal child membership only from evidence such as explicit standalone save/manual add/non-null score, including score zero. Public auto-imported discography rows do not become personal saves.
- [ ] Preserve separate artist/album/song scores and overall reviews; detect conflicts between standalone and nested ratings. Preserve original rows until mapping reconciles.
- [ ] Migrate artist statuses to following-only semantics, retaining original values for audit when needed; never create fake listening songs or experiences.
- [ ] Preserve all episode and season ownership, scores and watched_on data. New caught-up operation writes only changed eligible progress marks.
- [ ] Prune only search-keyed ProviderCache rows after taxonomy audit; saved follow-up/enrichment cache remains where still used. Document retention and orphan cleanup independent of personal membership removal.

## Migration execution and rollback

- [ ] One migration owner reserves revision order. Travel/Media agents propose model/schema diffs and backfill functions but never independently create conflicting heads.
- [ ] Capture baseline counts, IDs, score/review digests, PTO totals, ownership and encrypted-record byte digests from disposable representative databases.
- [ ] Write an offline migration plan/report before changes. Take a verified consistent backup using existing tooling.
- [ ] Prefer expand/backfill/validate/contract internally; final refactor PR can delete obsolete runtime paths after all tests run. Keep applied revision history.
- [ ] Exercise fresh DB → head, current populated DB → head, historical adoption fixture → head, repeated migration, interrupted failure/rollback, and schema drift rejection.
- [ ] Verify row counts and preserved personal values after backfill; report ambiguous/unallocated data instead of dropping it.
- [ ] Check SQLite foreign keys/indexes, busy timeout, WAL, ownership constraints, migration lock duration, and bounded query behavior on realistic fixtures.
- [ ] Previous-image compatibility is recorded only for genuinely compatible expand-only revisions. Destructive rename/drop/retype cannot claim rollback compatibility.
- [ ] If final contract migration breaks previous image, release uses maintenance/no-writer window and backup restore for rollback; document both database and image restoration.
- [ ] Startup only verifies schema compatibility and serves; never migrates or creates tables implicitly.

## Single-PR release readiness

One branch integrates frontend, backend, command mapping, schema, docs and image. One final tested image is promoted. A PR merge alone does not atomically migrate a live database: use the existing migrate/deploy operational sequence with readiness checks. Deployment and real-data operations are implementation release steps, not part of this planning change.

Done when no new code depends on import-time engines, copied middleware internals, remote loopback auth, or search side effects; all personal records survive migration; the assembled app passes domain and integration suites locally.
