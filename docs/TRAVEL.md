# Travel

Travel's domain code stays in `apps/travel`, with Angular presentation in `frontend` and FastAPI routers/services in `backend`. The root site serves `/travel/`; API routes retain `/travel/api`. Identity, CSRF and the request database session come from the server platform in-process. Trip costs never write Finance records or alter net worth.

Use the root workflow in [Development](DEVELOPMENT.md). There is one service and one SQLite database; there is no standalone Travel deployment. Sign-in is `/auth/login`, and the persistent Hub control returns to `/hub`. Use the username dropdown to open Settings or sign out. Settings groups Flight schedules, calendar subscriptions and Travel preferences under Connections.

## Trips and forms

A trip spans departure through return, inclusive. Plan a trip starts with a flight number and date, one calendar file, or typed dates and a destination. Add destination changes on the first date at the next city; keep one optional trip-name editor. Every destination needs a name. Reversed dates cannot save. Same-day and one-night trips have explicit wording.

Save draft on Plan a trip stores one confirmed outbound leg when the return is still unknown. The draft keeps the departure date, that leg, and a return date or destination city only when those fields were typed. An arrival time does not become the return date, and the draft does not create a PTO charge. Saving a complete trip still requires the return date and still allocates PTO. A failed or late draft save leaves the current form in place. Signing out clears the private in-memory draft.

Trip detail reads transport, lodging, activities, parking, notes, and reminders on their local day. Add on that day reuses the trip. Notes, reminders, parking and extra costs use optional editors. Failed saves keep drafts; route and document exit guards protect unsaved changes. A completed create retries the same database-backed user/request key, including after process restarts and concurrent submissions. Missing keys intentionally create separate trips. Deleting a trip removes its children and PTO usage after confirmation; individual rows offer Undo with a retained snapshot and an explicit retry if restoration fails.

Costs on transport, plan and parking rows roll up automatically. Extra budget lines represent other costs. Totals stay separate by currency. Parking records whether it is necessary and booked. Home lists open reminders, needed unbooked parking and PTO overlaps.

Upcoming and past trips are ticket postcards. A card states the saved date span and a status of Away now, Upcoming, or Past, plus one next action from that phase. It names a city, an airport, or lodging only from saved stays and flight records. The trip title is not a destination. An empty itinerary, missing coordinates, or failed map tiles still leave that text on the trip.

## Flights and maps

A valid flight number and departure date trigger one bounded FlightAware AeroAPI lookup. Near departure uses `GET /flights/{ident}` from 10 days ago through 1 day ahead. The UTC day two days ahead, and a later date whose exclusive end is within one calendar year, uses `GET /schedules/{date_start}/{date_end}`. Dates from 2011-01-01 up to that operational window use `GET /history/flights/{ident}`. Dates before 2011-01-01, and schedules ends past the calendar-year ceiling, are unavailable and do not call the provider. Each lookup is one page with a 20-second timeout. A published schedule has no airport timezone and says so. Multiple candidates, including different routes and codeshares, need an explicit choice. Scheduled, estimated and actual times stay distinct. Manual edits survive a later lookup; Use flight schedule deliberately resets overrides. A refresh updates the same saved leg and does not insert another. Missing key, unsupported date, rejected key, historical entitlement, throttling, timeout and no match remain separate from suite authentication. Plan a trip proposes that route and those local times before any save. The user chooses a matching flight, a new draft, or an existing trip. An inferred arrival airport is not the destination city until the user accepts it. Choosing a new trip does not invent a return date or charge PTO. FlightAware settings can open over the transport editor or that flight draft. Back restores focus and keeps the current in-memory trip and flight draft. Saved keys stay on the server. The adapter contract is [TUX-02](../planning/implementation/issues/TUX-02.md).

One flight calendar file is a supported VEVENT with a time zone and a leg identity. Plan a trip previews that booking and matches it to a saved leg before any draft or trip write. The same booking offers the existing leg instead of a second copy. Malformed, oversized, and ambiguous-timezone files stay in the preview and write nothing. The preview does not invent a return date or a PTO charge, and it does not call a schedule provider.

Places resolve only after explicit search and selection. Normal trip reads never geocode. Nominatim requests use an identifying User-Agent, aggregate one-second pacing and a cache with positive/empty expiry. Maps use the app-owned Leaflet DOM adaptation under the enforced private CSP and Trusted Types policy. Tiles receive only the site origin as Referer. Tile/library failures explain the failure, retain a textual place list and expose recovery. Tests use synthetic tiles.

## PTO

Each trip date stores 0, 0.5 or 1 PTO days. Weekdays start at 1; Saturday/Sunday start at 0. Turning PTO off retains selections. Date edits retain intersecting choices and default newly added dates. Trip, calendar, home and forecast use the same dated charges. Overlaps are reported with dates and labels rather than silently merged. The forecast lists those server points, including the accrual boundary, in each point's own day and hour text. Carry, cap, and reset stay on the policy card. A trip shows each overlap on its day.

A saved balance is the balance at the end of `balance_as_of`. Daily accrual, the default for existing and new policies, begins the next day: annual amount /365, monthly amount ×12/365, semimonthly ×24/365, biweekly /14 and weekly /7. Scheduled posting is opt-in. It posts the whole amount on an explicit first date and then on that cadence, and it does not fill dates on or before the balance date. Same-day order is the policy-year drop, then accrual, then that day's charge. Hours convert using `hours_per_day`; a cap pauses accrual while reached. Dated trip charges apply on their dates; historical/manual aggregate usage retains its recorded start-date semantics.

Legacy custom trip totals remain explicitly unallocated until the owner confirms a dated allocation. Migration preserves the original total, including zero/fractions. It never guesses which dates a custom amount meant. This is a planning projection, not payroll. [Migrations](MIGRATIONS.md) documents the unified schema.
